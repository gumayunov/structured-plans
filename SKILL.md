# Структурированные дизайны и планы

Скил меняет в workflow superpowers четыре вещи: куда сохранять дизайн и план, как
нумеровать задачи, где вести прогресс и как дизайн и план связаны с документацией проекта. Содержание дизайна и структура плана остаются
по brainstorming и writing-plans: их требования не отменять и шаблон плана не переписывать.

## Обозначения

| Обозначение | Что это | Пример |
|-------------|---------|--------|
| `<DDD>` | номер дизайна, три цифры | `003` |
| `<slug>` | короткое имя дизайна: латиница, lowercase, kebab-case | `widget-auth` |
| `<PP>` | номер фазы, две цифры; `00` для плана без фаз | `01` |
| `<TT>` | номер задачи внутри фазы, две цифры, с `01` | `05` |
| ID задачи | `T<DDD>-<PP>-<TT>` | `T003-01-05` |
| `<N>` | номер задачи в заголовке плана: `<TT>` без ведущего нуля | `5` |
| каталог дизайна | `docs/designs/<DDD>-<slug>/` от корня репозитория | `docs/designs/003-widget-auth/` |

```
docs/designs/
├── 000-widget-auth/         # план без фаз
│   ├── design.md
│   ├── plan.md
│   └── progress.md
└── 001-billing-export/      # план с фазами
    ├── design.md
    ├── phase-001-00.md
    ├── phase-001-01.md
    └── progress.md
```

| Файл | Заменяет у superpowers | Когда создаётся |
|------|------------------------|-----------------|
| `design.md` | `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` | шаг 1 |
| `plan.md` | `docs/superpowers/plans/YYYY-MM-DD-<feature>.md` | шаг 2, план без фаз |
| `phase-<DDD>-<PP>.md` | тот же файл плана, по одному на фазу | шаг 2, план с фазами |
| `progress.md` | — | шаг 1, задачи добавляются на шаге 2 |

Шаблоны `design.md`, дополнений файла фазы и `progress.md` — в
[references/templates.md](references/templates.md).

## Дизайн и план — история, документация — артефакт

Дизайн и план фиксируют решение на момент принятия: после мержа их не правят, на них
ссылаются как на справку — «решение принято в дизайне 004». Систему такой, какая она
есть, описывают живые документы проекта: правила для агентов (`CLAUDE.md`, `AGENTS.md`),
справочники, карта архитектуры. Их правка — такая же работа, как код: дизайн называет
живые документы, которые изменение сделает неверными (раздел «Документация» шаблона), а
план ставит правку каждого в задачу, после которой он устаревает. Какие документы живые,
проект описывает сам; если не описывает — живыми считать `CLAUDE.md`, `AGENTS.md` и
`README.md` каталогов.

## Шаг 0. Проверить старые каталоги

Выполнить перед первым сохранением файла в сессии:

```
ls -d docs/superpowers docs/plans docs/designs 2>/dev/null
```

| Признак | Действие |
|---------|----------|
| Пустой вывод или только `docs/designs` | Перейти к нужному шагу |
| Есть `docs/superpowers` или `docs/plans` | Новые файлы писать в `docs/designs/`. Старые не трогать и не переносить. Сказать пользователю одной строкой: «Старые дизайны и планы остались в `<каталог>`; перенести их в docs/designs/ можно по запросу» |
| Надо выполнить план, который лежит в `docs/superpowers/` или `docs/plans/` | Выполнять его на месте по executing-plans или subagent-driven-development. Шаги 1–3 этого скила не применять |
| Пользователь просит перенести старые файлы | Выполнить [references/migration.md](references/migration.md) |

Затем проверить, не игнорирует ли git каталог дизайнов (многие держат планы локально
через глобальный `~/.gitignore`):

```
git check-ignore -q docs/designs/x.md && echo ignored || echo tracked
```

| Вывод | Действие |
|-------|----------|
| `tracked` | Коммитить в шагах 1–3 как написано |
| `ignored` | Пункты «Закоммитить» в шагах 1–3 пропускать. `git add -f` не использовать. В сообщениях пользователю вместо «закоммичено» писать «сохранено локально, git игнорирует docs/designs» |

## Шаг 1. Сохранить дизайн (brainstorming)

Выполнять вместо абзаца «Where it goes» в разделе brainstorming «The Written Design» —
когда подход выбран и пора записывать дизайн: короткий для небольшой правки или полный
для проекта.

1. Вычислить номер нового дизайна:
   ```
   find docs/designs -maxdepth 1 -type d \( -name '[0-9][0-9]-*' -o -name '[0-9][0-9][0-9]-*' \) 2>/dev/null | sed -E 's|.*/([0-9]+)-.*|\1|' | sort -n | tail -1 | awk '{printf "%03d\n", $1+1} END {if (NR==0) print "000"}'
   ```
   Вывод — три цифры, это `<DDD>`. `000` значит, что дизайнов ещё нет. Каталоги
   с двузначным номером от прежней версии скила (`03-widget-auth`) команда тоже
   учитывает, и нумерация продолжается после них.
2. Создать каталог: `mkdir -p docs/designs/<DDD>-<slug>`. Если каталог с таким `<DDD>`
   уже есть — повторить пункт 1, существующие файлы не перезаписывать.
3. Записать `docs/designs/<DDD>-<slug>/design.md` по шаблону.
4. Записать `docs/designs/<DDD>-<slug>/progress.md` — только шапку из шаблона, без
   сводки и задач.
5. Для проекта выполнить builder check из brainstorming и внести его итоги
   в `design.md`. Для небольшой правки builder check не нужен.
6. Закоммитить: `git add docs/designs/<DDD>-<slug>/`, затем `git commit` с сообщением
   по конвенции репозитория.
7. Отдавая дизайн пользователю на одобрение (HARD-GATE в brainstorming), назвать путь
   `docs/designs/<DDD>-<slug>/design.md`. Правки после одобрения коммитить так же — до мержа
   PR. После мержа дизайн не правится: новое решение — новый дизайн или живой документ.

## Шаг 2. Сохранить план (writing-plans)

1. Прочитать `docs/designs/<DDD>-<slug>/design.md`. Если пользователь не назвал дизайн —
   взять каталог с наибольшим `<DDD>`. Если в нём уже есть `plan.md` или `phase-*.md` —
   спросить пользователя, какой дизайн планировать.
2. Выбрать форму плана:

   | Признак | Форма |
   |---------|-------|
   | Дизайн описывает несколько независимых подсистем | Не фазы. Предложить разбить на отдельные дизайны, как требует Scope Check в writing-plans |
   | Работа делится на этапы, и каждый этап мержится и проверяется отдельно | Фазы: файлы `phase-<DDD>-<PP>.md`, `<PP>` с `00` |
   | Пользователь просит фазы | Фазы |
   | В плане больше 10 задач | Фазы |
   | План длиннее 2000 строк | Фазы |
   | Остальные случаи | Один файл `plan.md`, `<PP>` = `00` |

   Фаза должна выполняться за один сеанс, поэтому в ней не больше 10 задач и не больше
   2000 строк. Если этап больше — разбить его на несколько фаз. Граница фазы — после
   задачи, на которой все проверки проходят и изменения можно смержить.

3. Написать план строго по writing-plans: обязательная шапка, `Global Constraints`,
   `Review Focus`, у задач `Files` и `Interfaces`, шаги с `- [ ]`. Отличаются только
   три вещи:
   - заголовок задачи `### Task <N>: T<DDD>-<PP>-<TT> — <название>`, например
     `### Task 5: T003-01-05 — Валидировать запрос`. Префикс `Task <N>:` не убирать:
     по нему `task-brief` из subagent-driven-development находит задачу. Ссылки на задачи
     в тексте — по ID;
   - в поле `**Spec:**` шапки — путь `docs/designs/<DDD>-<slug>/design.md`;
   - в файле фазы — разделы из шаблона «Дополнения файла фазы»;
   - каждый живой документ из раздела «Документация» дизайна входит в `Files: Modify`
     задачи, после которой он устаревает. Отдельной задачи «обновить документацию» в конце
     плана нет: документ, отложенный на потом, расходится с кодом в промежуточных коммитах.
4. Проверить размер файлов плана:
   ```
   find docs/designs/<DDD>-<slug> \( -name plan.md -o -name 'phase-*.md' \) -exec wc -l {} +
   find docs/designs/<DDD>-<slug> \( -name plan.md -o -name 'phase-*.md' \) -exec grep -cE '^### Task [0-9]+: T[0-9]{2,3}-' {} +
   ```
   Первая команда выводит число строк в каждом файле, вторая — число задач. Файл длиннее
   2000 строк или с числом задач больше 10 — разбить на фазы по правилу из пункта 2
   и повторить проверку.
5. Добавить в `progress.md` сводку и все задачи плана по шаблону.
6. Проверить, что в `progress.md` попали все задачи:
   ```
   grep -hE '^### Task [0-9]+: T[0-9]{2,3}-' docs/designs/<DDD>-<slug>/*.md | wc -l
   grep -c '^- \[.\] `T' docs/designs/<DDD>-<slug>/progress.md
   ```
   Числа должны совпасть. Не совпали — дописать в `progress.md` недостающие задачи.
7. Выполнить Self-Review из writing-plans.
8. Закоммитить: `git add docs/designs/<DDD>-<slug>/`, затем `git commit` с сообщением
   по конвенции репозитория.
9. В Execution Handoff назвать путь `plan.md` или файла первой фазы.

## Шаг 3. Вести прогресс при выполнении плана

Выполнять вместе с subagent-driven-development или executing-plans, когда план лежит
в `docs/designs/`.

1. План с фазами выполнять по одному файлу фазы, по возрастанию `<PP>`. Следующую фазу
   начинать, когда все задачи предыдущей отмечены `[x]` в `progress.md`.
2. Перед первой задачей проверить заголовки задач в файле плана:
   ```
   grep -cE '^### Task [0-9]+:' <файл плана>
   grep -cE '^### T[0-9]{2,3}-' <файл плана>
   ```
   Вторая команда вывела не `0` — план в старом формате. Скрипты `task-brief`
   и `task-done` такие задачи не находят. Привести заголовки к формату шага 2:
   ```
   perl -pi -e 's/^### (T\d{2,3}-\d{2}-(\d{2})):\s*/sprintf("### Task %d: %s — ", $2, $1)/e' <файл плана>
   ```
   и повторить проверку: первая команда выводит число задач, вторая — `0`. Изменённый
   файл плана закоммитить вместе с `progress.md` в пункте 7.
3. Номер задачи для скриптов и журнала — `<N>` из заголовка: `task-brief <файл> 5`,
   `task-done <файл> 5 …`. Журнал ведут сами скилы выполнения
   (`.superpowers/sdd/<имя файла плана>/progress.md`, строки `Task <N>: complete …`).
   Формат журнала не менять: по нему скилы находят место продолжения.
4. Задача считается завершённой:

   | Скил выполнения | Момент |
   |-----------------|--------|
   | subagent-driven-development | ревью задачи вернулось чистым и в журнале появилась строка `Task <N>: complete` |
   | executing-plans | `task-done` прошёл и записал строку `Task <N>: complete` |

5. Сразу после завершения задачи в `progress.md`:
   - в строке задачи заменить `- [ ]` на `- [x]`;
   - пересчитать строку этой фазы в таблице «Сводка» по правилу из шаблона.
6. После сжатия контекста место продолжения искать по журналу и `git log`, как требуют
   скилы выполнения. Если `progress.md` с ними расходится — исправить `progress.md`.
7. Закоммитить `progress.md` после завершения каждой фазы и в конце плана:
   `git add docs/designs/<DDD>-<slug>/progress.md` (и файл плана, если в пункте 2
   менялись заголовки), затем `git commit`.
