# Перенос старых дизайнов и планов в docs/designs/

Выполнять только по явной просьбе пользователя. Без просьбы старые файлы не трогать.

- [Собрать список файлов](#1-собрать-список-файлов)
- [Разбить файлы на дизайны](#2-разбить-файлы-на-дизайны)
- [Разложить файлы дизайна](#3-разложить-файлы-дизайна)
- [Согласовать таблицу переноса](#4-согласовать-таблицу-переноса)
- [Переместить файлы](#5-переместить-файлы)
- [Переименовать задачи в планах](#6-переименовать-задачи-в-планах)

- [Убрать пустые каталоги](#9-убрать-пустые-каталоги)
- [Проверить и закоммитить](#10-проверить-и-закоммитить)

Откуда переносятся файлы:

| Каталог | Имена файлов |
|---------|--------------|
| `docs/superpowers/specs/` | `YYYY-MM-DD-<topic>-design.md` — дизайн |
| `docs/superpowers/plans/` | `YYYY-MM-DD-<feature>.md` — план |
| `docs/plans/` (старые версии superpowers) | `YYYY-MM-DD-<topic>-design.md` — дизайн, остальные `YYYY-MM-DD-<name>.md` — план |

## 1. Собрать список файлов

```
find docs/superpowers/specs docs/superpowers/plans docs/plans -maxdepth 1 -type f -name '*.md' 2>/dev/null | sort
```

Пустой вывод — переносить нечего, сказать об этом пользователю и закончить.

## 2. Разбить файлы на дизайны

1. Для каждого файла вычислить ключ: имя файла без даты `YYYY-MM-DD-`, без суффикса
   `-design` и без `.md`. Пример: `2025-03-14-widget-auth-design.md` → `widget-auth`.
2. Файлы с одинаковым ключом — один дизайн. Ключ становится `<slug>`.
3. Если ключи явно про одну задачу, но не совпадают (`widget-auth` и `widget-auth-impl`) —
   не объединять самостоятельно, вынести вопрос пользователю в пункте 4.
4. Упорядочить дизайны по самой ранней дате среди их файлов.
5. Первый номер `<DDD>` — вывод команды из шага 1.1 SKILL.md, дальше по порядку +1.

## 3. Разложить файлы дизайна

| Что есть у дизайна | Новые файлы |
|--------------------|-------------|
| Один файл дизайна | `design.md` |
| Один план | `plan.md`, `<PP>` = `00` |
| Несколько планов | Фазы: `phase-<DDD>-<PP>.md`, `<PP>` с `00` по дате плана |
| Плана нет | Только `design.md` и `progress.md` с шапкой |
| Дизайна нет | `plan.md` без `design.md`; в шапке `progress.md` дописать «design.md не сохранился» |

## 4. Согласовать таблицу переноса

Показать пользователю таблицу и дождаться подтверждения. До подтверждения ничего
не перемещать.

Перед показом таблицы проверить, что будет с файлами в git:

```
git check-ignore -q docs/designs/x.md && echo ignored || echo tracked
git ls-files docs/superpowers docs/plans
```

| Признак | Что добавить к таблице |
|---------|------------------------|
| `tracked` | Ничего |
| `ignored`, `git ls-files` пустой | «docs/designs игнорируется git, файлы останутся локальными, как и сейчас» |
| `ignored`, `git ls-files` выводит файлы | Вопрос: «docs/designs игнорируется git, а перечисленные файлы сейчас в репозитории. Как переносить? (а) оставить их в репозитории — git продолжит отслеживать перенесённые файлы, а новые progress.md останутся локальными; (б) сделать локальными — коммит удалит их из репозитория у всех». Без ответа не переносить |

```markdown
| Старый файл | Новый файл |
|-------------|------------|
| docs/superpowers/specs/2025-03-14-widget-auth-design.md | docs/designs/000-widget-auth/design.md |
| docs/superpowers/plans/2025-03-15-widget-auth.md | docs/designs/000-widget-auth/plan.md |
```

Если пользователь правит таблицу — перенести по исправленной.

## 5. Переместить файлы

Для каждой строки таблицы создать каталог: `mkdir -p docs/designs/<DDD>-<slug>`.
Затем переместить файл командой из таблицы:

| Признак | Команда |
|---------|---------|
| Пользователь выбрал (б) в пункте 4 | `mv <старый файл> docs/designs/<DDD>-<slug>/<новое имя>`, затем `git rm --cached <старый файл>` |
| Остальные случаи | `git mv <старый файл> docs/designs/<DDD>-<slug>/<новое имя>` — история файла сохранится |
| `git mv` ответил `not under version control` | `mv <старый файл> docs/designs/<DDD>-<slug>/<новое имя>` |

## 6. Переименовать задачи в планах

1. Для каждого `plan.md` и `phase-<DDD>-<PP>.md` запомнить число задач:
   `grep -c '^### Task [0-9]' <файл>`.
2. Добавить ID в заголовки `### Task N:`:
   ```
   perl -pi -e 's/^### Task (\d+):\s*/sprintf("### Task %d: T%s-%s-%02d — ", $1, "<DDD>", "<PP>", $1)/e' <файл>
   ```
3. Проверить: `grep -cE '^### Task [0-9]+: T[0-9]{3}-' <файл>` равно числу из пункта 1.
4. Найти упоминания задач в тексте, кроме заголовков: `grep -nE 'Task [0-9]' <файл> | grep -v ':### Task'`.
   Каждое заменить на ID той же задачи вручную.
5. В шапке плана указать `**Spec:** docs/designs/<DDD>-<slug>/design.md`, если
   `design.md` есть: заменить значение поля или добавить строку после `**Tech Stack:**`.

## 7. Создать progress.md

Для каждого дизайна записать `progress.md` по шаблону из
[templates.md](templates.md). Статус задачи:

| Шаги задачи в плане | Статус в progress.md |
|---------------------|----------------------|
| Все `- [x]` | `[x]` |
| Хотя бы один `- [ ]` | `[ ]` |
| Шагов с чекбоксами нет | `[ ]`, и спросить пользователя в пункте 10 |

Журналы `.superpowers/sdd/` для статусов не использовать: они игнорируются git, есть
только на машине, где выполняли план, и привязаны к старому пути файла плана.

## 8. Обновить ссылки на старые пути

```
grep -rn --include='*.md' -e 'docs/superpowers/specs/' -e 'docs/superpowers/plans/' -e 'docs/plans/' . | grep -v '^./.git/'
```

Каждую найденную ссылку заменить на новый путь из таблицы пункта 4. Пустой вывод —
ссылок нет.

## 9. Убрать пустые каталоги

```
find docs/superpowers/specs docs/superpowers/plans docs/plans -type d -empty -delete 2>/dev/null
find docs/superpowers -type d -empty -delete 2>/dev/null
ls docs/superpowers docs/plans 2>/dev/null
```

Пустой вывод последней команды — старых каталогов не осталось. Если в них остались
другие файлы — не удалять, перечислить их пользователю.

## 10. Проверить и закоммитить

1. Для каждого дизайна выполнить проверку из шага 2.6 SKILL.md: числа должны совпасть.
2. Показать пользователю задачи со статусом под вопросом из пункта 7.
3. Закоммитить одним коммитом: `git add -A docs/` и файлы с исправленными ссылками,
   затем `git commit` с сообщением по конвенции репозитория. Если docs/designs
   игнорируется git и `git status --short` пуст — коммитить нечего, сказать об этом
   пользователю. `git add -f` не использовать.
